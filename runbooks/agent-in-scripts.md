# Agent-in-scripts doctrine, where `claude -p` is allowed, where it isn't

The market-intel scripts evolved as 100% deterministic infrastructure (gh-api,
HTTP, regex, file IO). After v0.25 the question came up: can we make scripts
smarter by calling `claude -p` (headless Claude Code) from inside them?

**Yes, but only on the helper side, never on the gate side.** This document is
the rule.

---

## The line

PHILOSOPHY P4 (实测胜于记忆, 证据胜于断言) says:

> "the deepest failure mode of an LLM system is confident fabrication. Truth must
> come from an independent deterministic source, verified by a check the model
> cannot talk its way past, and the editor is never its own verifier."

The line cuts the script population in two:

### Side A, fail-closed gates · LLM FORBIDDEN

Any script that **blocks a release, sweep, install, or commit** when it returns
non-zero. Replacing its check with LLM judgment opens a "model talks its way
past" failure mode.

| Script | Why it's a gate |
|---|---|
| `tools/verify_matrix.py` GHACTIVE | Activity check on every github repo in the matrix. Final release gate. |
| `tools/l0_verify.py` | Per-candidate URL/repo deterministic check. Pre-land gate. |
| `tools/check_doc_drift.py` (fail-level checks) | Derived-field drift. Release gate at step 5c. |
| `tools/check_p5_drift.py` | One-line grep for P5 violation. Cleanup-pass gate. |
| `market-intel-config/scripts/sync-check.py` | 7-bucket drift on companion-config. Release gate at step 5. |
| `tools/sidecar_from_changelog.py` (the primary slug-to-doc resolution) | Forms the contract config-bridge consumes. Fuzzy fallback is OK, see helper side. |

**Rule**: these scripts MUST stay deterministic. Adding a `claude -p` call is a
P4 violation. If you genuinely need LLM judgment in this area, build a SEPARATE
helper that runs `BEFORE` the gate and outputs structured data; the gate then
checks the data.

### Side B, draft & helper scripts · LLM ALLOWED

Any script whose output is **reviewed by a human before it has any effect**.
These don't gate anything; they save the human time on initial drafting.

| Script | Role | Output |
|---|---|---|
| `tools/changelog_draft.py` | Drafts CHANGELOG entry from git log + diff stats. | Markdown to stdout. User edits + pastes. |
| `tools/incident_helper.py` | Fills the 6-step `runbooks/fix-broken-tool.md` runbook. | 6 artifacts (live-runs JSON / D-code / shard edit / etc.) printed. User reviews; `--apply` is opt-in per step. |
| `tools/sidecar_from_changelog.py` `--llm-fallback` (future) | When fuzzy slug matching fails, LLM suggests the most likely tool doc. | Adds suggestions to the `unresolved` array. User verifies before consuming. |
| `tools/tool_doc_draft.py` (future) | Reads an upstream repo's README and drafts a `tools/<slug>.md`. | Markdown to stdout. User edits + commits. |
| `tools/discover.py` E3 noise filter (future) | LLM filters the 50 HF Spaces hits for "agent tool likely" vs "model demo". | Reduced candidate list piped to inbox. |
| `tools/check_doc_drift.py` `--narrative-check` (future, warn-level only) | LLM reads README + SKILL.md and judges if narrative still describes the system. | warn line. Never fail-level. |

**Rule**: these scripts MUST print explicitly:

```
Generated by <name>.py — REVIEW + EDIT before committing.
Per PHILOSOPHY P4: this is a DRAFT, not a gate.
```

And they MUST have an `--apply` flag (default off) for any state mutation.

### Side C, soft warn-level alerts · LLM TOLERATED

Scripts that emit only **warnings**, never blocking. LLM judgment is acceptable
because the human decides whether to act on the warning.

Examples (future):
- `check_doc_drift.py` PHILOSOPHY-amendment-age narrative check
- `feedback-bump.py` ambiguous `outcome` classification (e.g. user wrote `unverifiable` → suggest mapping to `barrier_found`)
- Refresh-protocol cleanup pass's "README narrative vs reality" fork agent

These can call `claude -p` freely. The warn output goes to the cleanup pass /
release log; no decision is taken automatically.

## The pattern, when to add LLM to a script

Ask three questions:

1. **Does it block anything?** If yes → P4 violation, don't add LLM. Make a
   separate draft helper instead.
2. **Is the output applied directly, or reviewed first?** Direct apply → LLM
   forbidden unless `--apply` is opt-in. Reviewed first → LLM OK.
3. **Could a hallucinated answer cause silent matrix degradation?** If yes → no.
   If at-worst the human sees garbage and re-runs → OK.

If all three answers point toward LLM-OK, add it. Otherwise stay deterministic.

## Invocation pattern (canonical)

For Python scripts calling `claude -p`:

```python
import subprocess
prompt = build_prompt()
# Pipe the prompt via stdin to avoid command-line length / quoting issues.
result = subprocess.run(
    ["claude", "-p", "--output-format", "text"],
    input=prompt, capture_output=True, text=True, encoding="utf-8",
    timeout=120,
)
if result.returncode != 0:
    sys.exit(3)  # claude not available or errored
draft = result.stdout
```

For PowerShell scripts (release.ps1 won't call LLM directly per P4, but
ancillary helpers might):

```powershell
$prompt = Get-Content tmp/prompt.md -Raw
$draft = $prompt | claude -p --output-format text
```

## What this rule prevents

Without this doctrine, the slippery slope is:
1. "Let's have verify_matrix use claude -p to be smarter about ambiguous repos."
2. → LLM occasionally hallucinates that a 404 repo "looks fine", silent drift in.
3. → Matrix degrades; gate has been talked past.

With this doctrine, that conversation is short: "verify_matrix is Side A; the
answer is no. If you want smarter triage, build a Side B draft helper that runs
before verify_matrix and outputs structured data verify_matrix then deterministically
checks."

---

## How to add a new LLM-using script

1. Decide which side: A (no), B (draft + review), or C (warn-only).
2. If A: don't. Find a B/C angle.
3. If B: implement, add `--apply` opt-in flag, add the standard "DRAFT, not gate"
   footer to all output.
4. If C: implement; warn-only output.
5. Add a row to the appropriate table in this runbook.
6. If it's invoked from `release.ps1` or refresh-protocol, document the position.

---

## When NOT to use claude -p

- When the answer is in a deterministic source you already have (gh-api gives
  pushed_at, don't ask LLM "is this repo active")
- When the answer is binary and the wrong answer breaks something (URL exists or
  doesn't, gh-api answers definitively)
- When the cost per call matters (cleanup pass already calls Claude for narrative
  freshness; don't multiply)
- When the user can't see the output before it takes effect

## Trigger

This runbook is read:
- By anyone proposing to add LLM to a script (mandatory)
- During refresh-protocol cleanup pass (annual review of LLM usage)
- When `check_doc_drift.py` flags this file as stale (>12mo)

If the line moves (P4 gets revised), that's a deliberate PHILOSOPHY amendment,
not a quiet violation here.
